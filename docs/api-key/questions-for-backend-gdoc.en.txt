Kong API Key Architecture — Open Questions

Context: Based on the three backend architecture docs shared by Shayan (README.md / implementation.md / cost-comparison.md), the following are questions the Explorer team needs to align on before building the in-browser API key management module. Sorted into three tiers: Blocking / Important / Clarifying.


═══════════════════════════════════════════
BLOCKING — work on the key management module cannot start until these are resolved
═══════════════════════════════════════════


1. How does our browser backend reach the Kong Admin API?

Doc §3.1 lists three candidate exposure options (internal HAProxy + IP allowlist / private DNS / in-cluster Kubernetes service) but does not pick one.

  • Which option is final?

  • What is the base URL? For testnet / staging / mainnet, what are the actual Admin API hostnames, ports, and TLS settings?
      ◦ Is kong-admin.{env}.movementnetwork.xyz just a placeholder, or the real name?
      ◦ Does the DNS resolve on the public internet, or only inside VPN / EKS?

  • If our browser backend is deployed as Next.js API Routes on Vercel (where egress IPs are not static), should we go through VPN / Tailscale / a dedicated link, or is it required that the browser backend run inside the EKS cluster?

  • How do we authenticate to the Admin API? mTLS? Static admin token? IAM? How does the browser backend hold and rotate credentials?

(This one determines the deployment shape of our browser backend — it is a prerequisite for everything else.)


2. Does the consumer / key data model support multiple keys + labels?

Our original design gives each key an independent label (e.g. "My bot", "Portfolio dashboard") and lets a user create multiple keys.

  • Is the model "one user → one Kong consumer → N keys" viable?

  • Can Kong key-auth key objects hold custom metadata (label, source, notes)? Is the tags field usable for this?

  • If not, should the kong_key_id → label mapping live in our browser backend's Neon database separately?

  • Can we get last_used_at timestamps directly from Kong, or only infer them from Mimir metrics?


3. What is the final key format?

The doc mentions supporting a custom prefix like mvmt_live_xxxxxxxxxxxx. We need to confirm:

  • Do testnet and mainnet use different prefixes (mvmt_test_ / mvmt_live_)?

  • What is the length and character set after the prefix? (Needed for masked display, e.g. mvmt_live_a3b2…f8c1)

  • Is the key generated by Kong, or generated by our browser backend and submitted to Kong?

  • Can the full key only be returned once on creation, and only the prefix be visible after that? ("Show once" is standard for security.)

4. Who owns tier upgrade / downgrade flows?

  • Can the browser backend directly call POST /consumer_groups/{tier}/consumers for self-service tier switching?

  • Or does it need to go through approval / payment / manual steps? What's the plan for now?

  • Do all new users default to free? What's the entry point for upgrading to standard / premium?

  • Is there a "trial" or "temporary quota boost" mechanism?


5. Source and dimensions of usage data

The doc says usage data comes from Prometheus/Mimir + Kong rate-limiting status. We need details:

  • Is the Mimir query endpoint exposed to our browser backend? How do we authenticate?

  • Does the Kong Prometheus plugin export metrics with a consumer label? (Required for per-user stats.)

  • Are route / service labels also present? (We want to show "which endpoint is called most" per user.)

  • Can REST and GraphQL traffic be distinguished?

  • How long is Mimir retention? (Determines the time range of our historical charts.)

  • Which endpoint gives real-time remaining quota? Can you share the response shape of /plugins/rate-limiting/status?

  • Can we also query 429-rejected requests?


6. How are anonymous / unauthenticated requests handled?

  • What is the exact rate limit for the anonymous consumer? (Doc says "10/min TBD".)

  • Does traffic from the Explorer site itself count as anonymous, or should Explorer use a dedicated service key?

  • If it's a service key: who manages it, who rotates it, where is it injected at deploy time?

  • If it's anonymous: does Explorer's traffic compete with end-user anonymous traffic for the same quota bucket?


7. Impact of GraphQL (Hasura) protection on Explorer itself

Explorer relies heavily on Hasura GraphQL today, and most of it is unauthenticated public queries. After Kong takes over:

  • Does the Explorer Apollo client need to start sending an API key?

  • Is the anonymous tier row limit (example: 50 rows) enough for Explorer's typical queries?
      ◦ Block / transaction list pages usually fetch 25–50 rows per request, sometimes more on pagination.

  • Does the api-anonymous role have access to every table Explorer needs? Any tables that will be blocked?

  • What tier does Explorer need to work normally? Should Explorer get its own api-explorer role?

  • How does Kong's x-hasura-role injection apply to Explorer's own GraphQL requests?

8. Current implementation status and interface details

  • Is the architecture above actually deployed yet? Where are testnet / mainnet in the rollout?

  • Is the Kong Admin API reachable today? Is there an environment (testnet / staging) our browser backend can use for integration testing?

  • Can the API key management module start work once testnet is ready, or do we need to wait for mainnet?

Doc §3.3 lists 7 Kong Admin API paths (/consumers, /consumers/{id}/key-auth, etc.), but those point at Kong's native Admin API. We need to clarify:

  • Which Kong version? (Different versions differ significantly in Admin API fields and behavior, especially around consumer_groups support.)

  • Does the browser backend talk directly to Kong's native Admin API, or will the backend team wrap it in a custom REST service? If wrapped, can you share an OpenAPI spec or curl examples?

  • How does the custom key prefix mvmt_live_xxx get implemented? By passing the key parameter to POST /consumers/{id}/key-auth, or does the browser backend generate it and submit it? Any character set / length constraints?

  • /plugins/rate-limiting/status (the last row in the §3.3 table) does not exist in Kong OSS's official Admin API. Is this:
      ◦ An endpoint the backend team plans to implement themselves?
      ◦ A typo, and the real path goes through Prometheus/Mimir?
      ◦ If it's via Mimir, can you share the exact metric names and PromQL examples?

  • Is the tags field enabled on Kong key-auth? (Determines whether label can live in Kong instead of our Neon.)

  • On key creation, is the key field in the response body only present that one time? On subsequent GET, does it only return the id and a masked value?


9. Are keys portable across networks (testnet / mainnet)?

  • Are consumers / keys per-network, or global across networks?

  • When Explorer's NetworkSelect switches networks, should the user see a different key list?

  • Are rate limit counters per-network or combined?

  • Is tier membership global or per-network?


10. CORS / direct browser calls

Explorer's API Docs page lets users click "Send Request" and hit the production API directly from the browser.

  • Will Kong DP open CORS to public browsers? Allow explorer.movementnetwork.xyz as an origin?

  • If not, Explorer has to run a proxy endpoint, which would consume Explorer's own quota — is there a way to avoid this?


11. Key rotation / leak revocation

  • Is there a native "regenerate key" operation, or do we implement it in the UI as delete + create?

  • After a key is revoked, how long does Kong DP take to invalidate it from cache? (Matters for response time on leaks.)

  • Are there audit logs we can surface to the user, e.g. "this key has been called recently from these IPs / UAs"?

  • Bulk revocation / emergency kill-switch endpoint?

Appendix: Our assumptions (please confirm ✅ / ❌)
═══════════════════════════════════════════

Design decisions we inferred from the docs — please confirm whether each is correct:

1. The browser backend is a stateless thin wrapper. Aside from the user_id ↔ kong_consumer_id mapping, it stores no key-related data of its own.

2. The plaintext API key is returned only once, in the create response. Afterwards the browser only shows the prefix.

3. Rate limits apply at the tier (consumer group) level, not per-key. All keys under the same consumer share a single quota bucket.

4. The browser backend does not participate in key validation — validation happens entirely at the Kong DP layer. Explorer does not need to maintain a local allow/deny list.

5. When a user upgrades their tier, the new tier takes effect immediately for all of that user's keys, with no additional action from the browser side.
